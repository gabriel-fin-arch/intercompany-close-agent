# Synthetic dataset

The CSVs in this folder are generated by `scripts/generate_synthetic_data.py`
(seed `14`, regenerate any time with `uv run python scripts/generate_synthetic_data.py`).
Nothing here is real: the group, its seven entities, and every transaction
are invented for this project.

## Why it's shaped this way

The dataset is built to mirror what an intercompany close actually looks
like in a multi-entity group running a consolidation tool (Lucanet, Oracle
EPM, or similar) fed by a source ERP:

- **`entities.csv`** -- the entity master. One entity, `ZA01`, is flagged
  `interfaced = false`. In a real close, most entities load their trial
  balance automatically from the source ERP; a handful don't, and get
  keyed in manually instead. Manual loads are exactly where reference typos
  and re-keying slips creep in, so `ZA01` gets an elevated chance of that
  kind of noise in the generator (see `anomaly_non_interfaced_noise`).

- **`trial_balance.csv`** -- one row per entity per GL account, using local
  (pre-mapping) account codes. The loader in `ingest/loaders.py` maps these
  onto a group standard chart of accounts, the same way a real mapping
  table sits between the source ERP's account codes and the consolidation
  tool's structure.

  The two intercompany accounts (`1000-IC-REC` and `2000-IC-PAY`) are
  **not** random: they're derived from the IC ledger below, because in a
  real close the GL's view of intercompany and the intercompany subledger
  are two records of the same balances and have to agree. One entity is
  then deliberately knocked out of balance -- a posting that reached the GL
  but never made it into the subledger, which is the everyday cause of a
  control account that won't tie at close. The `reconcile` step catches it.
  Every other account on the trial balance is filler; nothing reads it.

- **`ic_ledger.csv`** -- the intercompany ledger. Every genuine intercompany
  balance is booked twice: once by the entity that owns the transaction,
  once by its counterparty (a management fee, a product transfer, a
  royalty, an intercompany loan's interest accrual, or a recharge). Both
  legs should net to zero. Most of the pairs in this dataset have been
  deliberately broken on one leg, the way real intercompany balances break
  at close:

  | Anomaly | What it looks like |
  |---|---|
  | `fx_mismatch` | Counterparty converted the same balance at a slightly different rate |
  | `timing` | Counterparty booked its leg after the group's close cutoff, pushing it into the next accounting period |
  | `missing_counterparty` | Counterparty never booked a mirror leg at all |
  | `wrong_counterparty_code` | Counterparty booked the leg against the wrong group entity |
  | `rounding` | A cents-level rounding difference, inside a sane tolerance |
  | `sign_flip` | Counterparty booked a payable as a receivable (or vice versa) |
  | `non_interfaced_noise` | A manually-loaded entity re-keyed the reference with a typo |
  | `local_currency` | An affiliate reported in its own local currency instead of the group's USD |
  | `self_dealing` | Counterparty's booking mapped the balance to itself instead of the real entity |
  | `duplicate_reference` | An unrelated transaction reused the same reference number |

  Everything that *isn't* broken should match cleanly by
  `counterparty_code` + `reference` + `amount` within a small tolerance.
  That clean minority is what lets the matching engine focus its output on
  the balances that actually need attention.

  `self_dealing` and `duplicate_reference` are rare enough at the default
  anomaly rate (one of ten injectors, picked ~35% of the time) that most
  seeds never produce either one, even though they're two of the six
  exception types `docs/human-in-the-loop.md` leans on hardest to make its
  case. The generator forces one of each onto a random pair instead of
  leaving it to that roll -- see `FORCED_ANOMALIES` in
  `src/intercompany_close_agent/synthetic/generator.py`.

## Regenerating

```
uv run python scripts/generate_synthetic_data.py --seed 14 --pairs 26
```

Same seed always produces the same dataset. A different `--seed` or
`--pairs` gives a different-sized, differently-broken population -- useful
for stress-testing the matching tolerances against a larger set.
